# Class-Level Solution

出方案时对准**问题类别**和**机制**，不对准第一个 case，也不对准第一个 case 所属的领域。

固定顺序：**宿主 → 类别 → 机制 → 参数 → 验证**。

## 1. 判档

| 情形 | 做法 |
|---|---|
| 单点缺陷（off-by-one / 拼写 / 空指针 / 错常量）且不新增分支；无行为变化（格式化、重命名、注释、依赖升级、类型标注）；用户已说「只修这个 case」「先跑通」 | 跳过模板，改完补一句问题类别 |
| 改动收敛在一处，不动主路径结构 | 轻量档 |
| 动主路径、新增分支 / 兜底 / 默认值 / 错误处理，或跨模块 | 完整档 |

要写 `if`、加特判、加兜底、改默认值、动错误处理 → 不算跳过。拿不准就用完整档。
轻量档不豁免第 2 节的思考，只豁免写出来。

## 2. 四问（写不出就别动代码）

1. **宿主边界**：通用服务 / 领域应用 / 一次性脚本，一句话说清对外服务谁。判不出来**就问用户，不要默认通用服务**——默认通用 = 自行加码抽象。
   - 通用服务：领域词只许进适配器 / 配置 / 变化点
   - 领域应用：机制可含该领域的稳定概念，但仍不对准第一个 ticket
   - 一次性脚本：允许事例层，但要写明「只修这个 case」
2. **问题类别**：剥掉专有名词、具体用户、错误码、接口、业务域。归入 契约 / 状态 / 并发 / 超时 / 权限 / 兼容 / 资源 / 路由 / 校验，或自拟——必须是类别名，不是事例名或领域名。
3. **不变量**：机制永远保证什么。**必须能写出一个违反它的具体场景**；写不出说明它是同义反复（「机制保证有超时」不是不变量）。这个反例后面要变成测试用例。
4. **两个变体**：换皮后仍由同一套机制接住。**至少一个换域 / 租户 / 知识库**，不能两个都是同一领域的换问法。

四项写不全 = 格局太小，停下重述，不要用 `if` 特判开干。
领域专名出现在「机制」栏 = 失败，只能进「变化点 / 这个 case」。

**只升一层**：覆盖已出现的 + 宿主上明显即将出现的同类。没有第二个真实调用方，不做框架、不预留扩展点。

## 3. 输出模板

轻量档：

```markdown
问题类别：<一类失败>
机制：<一套机制怎么接住>
这个 case：<机制的一组参数>
```

完整档：

```markdown
宿主：<通用服务 / 领域应用 / 脚本> — <对外服务谁>
问题类别：<一类失败，不是一个 ticket，也不是一个领域>
不变量：<机制保证什么永远为真> ｜ 违反场景：<一个具体反例>
变体：<同域换皮>；<换域 / 换租户>
机制：<一套机制如何接住上述变体>
变化点：<阈值 / 规则 / 领域适配器>
这个 case：<只作为机制的一组参数>
验证：V1 <换域重放结论> ｜ V2 <固化不变量的用例/断言位置> ｜ V3 <领域词落在哪里>
不做：<假想十年后的平台 / 框架>
```

## 4. 验证闭环

给完方案不算完。三项全过才算「解决」，任一不过按对应动作处理。

**V1 换域重放**（落地前，思想实验）
取变体里换域那个，**只替换「这个 case」一栏的参数**，机制描述与主路径一个字不改。
- 过：仍成立 → 继续落地。
- 不过：机制里混进了领域假设 → 回第 2 节重述，不要靠加参数补救。
- 不要求真去实现第二个域。

**V2 不变量固化**（落地后，可执行）
把第 3 问那个违反场景写成一条能跑的检查：单测 / 契约校验 / 断言 / 校验器。
- 过：该用例在改动前失败、改动后通过。
- 不过：说明不变量是同义反复，或机制没真正接住 → 重写不变量，别改用例迁就实现。
- 无测试基建时退化为主路径上的显式前置校验或断言，并在方案里写明「未被测试固化」。

**V3 领域词隔离**（落地后，可扫描）
扫改动里的机制 / 主路径文件，查领域专名：剧集名、租户名、META 键、具体用户 ID、具体错误字符串、写死阈值。
- 过：这些词只出现在配置、规则表、适配器、测试数据里。
- 不过：把它挪出主路径，换成配置项或适配器。

**修不动时显式降级**：最小升层成本明显高于「再炸一次」的成本，就写一行
`已知窄解：<问题类别> — 下次会在 <哪里> 再炸一次`，
而不是假装升层成功，也不是硬升。

## 5. 审已有 patch

评审「太具体」的改动，按序走，不要一上来要求重写：

1. 指出它实际落在哪一层（事例 / 领域 / 机制）。
2. 给出它对应的问题类别，和一个它接不住的变体（换域那个）。
3. 提**最小升层**：`if` 能不能换成一条规则 / 一个配置项 / 一个适配器，主路径不动。
4. 用 V2 补一条固化不变量的用例——这是评审能留下的最小闭环。
5. 说明保持原样的代价，或按上面的格式记为「已知窄解」。

## 失败信号

- 为第一个报错加特判，并称之为方案
- 升层停在第一个 case 所属领域，领域词写进「机制」
- 用「换一种问法」代替「换一个调用方域」做 V1
- 不变量写不出违反场景，仍继续设计；或 V2 里改用例去迁就实现
- 宿主边界靠猜、默认通用服务，为不存在的调用方设计
- 把「通用」做成连升三层的平台；没有第二个调用方就预留扩展点
- 为了凑换域验收，真去实现第二个域
- 用具体错误字符串或业务域名当分类名
- 给拼写 / 依赖升级这类改动也套完整档

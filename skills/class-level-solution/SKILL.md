# Class-Level Solution

出方案时对准**问题类别**和**机制**，不对准第一个 case，也不对准第一个 case 所属的领域。

先标定**宿主系统**，再分类，再机制，最后才是这个 case 的参数。

用户只要一次性补丁时，明确说「只修这个 case」，再允许事例层方案。

## 何时跳过

下面的改动直接做，只在改完补一句问题类别，不套模板：

- 单点缺陷：off-by-one、拼写、空指针、错误的常量，且**不新增分支或判断路径**
- 无行为变化：格式化、重命名、注释、依赖升级、类型标注
- 用户已明确说「只修这个 case」/「先跑通」

一旦要写 `if`、加特判、加兜底、改默认值、动错误处理 → 不算跳过，走 hard gate。

## Hard gate

未同时写出下面四项，不得给出方案或动手改代码：

1. **宿主边界**（通用服务 / 领域应用 / 一次性脚本；一句话说清对外服务谁）
2. **问题类别**（剥掉专有名词、具体用户、具体错误码、具体接口、具体业务域）
3. **不变量**（机制必须永远保证什么）
4. **两个变体**（换皮后仍由同一套机制接住；至少一个必须换**域/租户/知识库**，不能两个都是同一领域的换问法）

写不出 = 格局太小。停下来重述，不要用 `if` 特判开干。

领域专有名词（某剧集、某 IP、某租户、某 META 键）出现在「机制」栏 = 失败，只能进「变化点 / 这个 case」。

两条判定：

- **宿主边界判不出来就问用户**，不要默认「通用服务」。默认通用 = 自行加码抽象。
- **不变量必须能写出一个违反它的具体场景**。写不出反例说明它是同义反复（「机制保证有超时」不是不变量）。

## 卡点

动手前必须能答：

1. 明天换个形态，这个问题还会再来吗？会 → 现在是推迟，不是解决。
2. 把输入换掉，方案还成立吗？只对这一个文件/接口/用户/错误码成立 → 太窄。
3. 在修机制，还是在修症状？
4. **换一个业务域/租户/知识库，方案还成立吗？** 只换同一领域的问法 → 升层停在领域，不是宿主。

## 流程

1. **标定宿主**：方案要落进哪个系统？它对外承诺服务谁？判不出来 → 问，不要猜。
   - 通用服务：领域词只许进适配器/配置/变化点
   - 领域应用：机制可以含该领域的稳定概念，但仍不能对准第一个 ticket
   - 一次性脚本：允许事例层，但必须写明「只修这个 case」
2. **升一层重述**：去掉对象名、数值、接口路径、**第一个业务域名词**，用抽象句重写问题。升层上限 = 宿主适用范围，不是 case 所属领域。
3. **归类**：契约 / 状态 / 并发 / 超时 / 权限 / 兼容 / 资源 / 路由 / 校验。归不进这些就自拟一类，但必须是类别名，不是事例名或领域名。
4. **找 2 个变体**：同类但不同皮。其中至少一个换域。三个变体不能被同一机制接住 → 还在打补丁。
5. **拆不变点 / 变化点**：
   - 不变点 = 机制（超时、校验、路由、降级、幂等、隔离）
   - 变化点 = 阈值、规则、领域适配器；做成配置/策略，不写进主路径 `if`
6. **只升一层**：覆盖已出现的 + 宿主上明显即将出现的同类问题。没有第二个真实调用方，不要先做框架。
7. **用机制验收**：换域验收是**思想实验**，只用来判断机制成不成立，**不要求本次实现另一个域**。想清楚就落这个 case 的参数。

## 落点

| 事例层（禁止当方案） | 领域层（通用宿主上同样禁止当方案） | 机制层（方案应落这里） |
|---|---|---|
| 这个 PDF / 这个用户 / 这个错误字符串 | 这个知识库 / 这个租户 / 这个 META 键 | 不可信输入、长任务、多实现路由、部分失败 |
| `timeout=60` 写死在一个接口 | 只为「第 N 季」写归一化 | 按任务类型配置超时与重试 |
| `if 特殊用户` | `if 某个知识库` | 用规则/策略表达差异 |
| 这个模型挂了写死兜底 | 把业务专名写进默认表 | 按能力路由 + 失败策略 |

方案卖的是机制，不是这一个 `if`，也不是这一个领域。

## 输出模板

**轻量档**（改动收敛在一处、不动主路径结构）：

```markdown
问题类别：<一类失败>
机制：<一套机制怎么接住>
这个 case：<机制的一组参数>
```

**完整档**（动主路径、新增分支/兜底、跨模块、需要评审）：

```markdown
宿主：<通用服务 / 领域应用 / 脚本> — <对外服务谁>
问题类别：<一类失败，不是一个 ticket，也不是一个领域>
不变量：<机制保证什么永远为真；附一句违反它的场景>
变体：<同域换皮>；<换域/换租户>
机制：<一套机制如何接住上述变体>
变化点：<阈值 / 规则 / 领域适配器>
这个 case：<只作为机制的一组参数>
验收：<换一个域/租户仍成立的那句话>
不做：<假想十年后的平台/框架>
```

拿不准档位就用完整档。轻量档不豁免 hard gate 的思考，只豁免写出来。

## 审已有 patch

评审一个「太具体」的改动时，按这个顺序，不要直接要求重写：

1. 指出它实际落在哪一层（事例 / 领域 / 机制）。
2. 给出它对应的问题类别，和一个它接不住的变体（换域那个）。
3. 提**最小升层**：能不能把 `if` 换成一条规则/一个配置项/一个适配器，主路径不动。
4. 说明保持原样的代价：下一个同类 case 会在哪里再炸一次。
5. 若最小升层的成本明显高于再炸一次的成本，结论就是「保留，记为已知窄解」——写清楚而不是硬升。

## 反模式

- 为第一个报错加特判，并称之为方案
- 升层停在第一个 case 所属领域，把领域词写进「机制」
- 用「换一种问法」代替「换一个调用方域」做验收
- 把「通用」做成连升三层的平台
- 没有第二个调用方就预留扩展点
- 用具体错误字符串或业务域名当分类名
- 解释不清「它保证什么」仍继续设计
- 宿主边界靠猜，默认当通用服务，为不存在的调用方设计
- 为了凑「换域验收」真去实现第二个域
- 给拼写/依赖升级这类改动也套四栏模板

# 源码分析与示例取证流程 v2

## 1. 扫描目标与接口身份

从仓库 README、依赖与项目入口识别架构、路由链、前缀及具体暴露协议。不要将内部函数误判为对外接口。排除构建目录、vendor/node_modules、临时文件和无关测试代码。对于多应用/多租户服务，将服务标识写入稳定 `key`。

- HTTP：逐一列出 Method + 完整 Path + 版本 + Controller。别忘了 Health/Status/Debug、认证票据及资源 CRUD。
- WebSocket：先确定连接端点，再逐个枚举客户端指令、回执、服务端推送、错误事件及关闭原因；不要仅列“连接入口”或一个大表格就算完成。应区分业务消息和协议 handshake。
- GraphQL：操作类型、Schema/Resolver、变量类型、Subscription payload、nullability。
- gRPC：服务/rpc、streaming、proto message、oneof/repeated、status。
- 动态注册、条件注册、多服务启动和网关路由必须结合注册点和配置判断，不能仅凭字符串查找决定接口存在与否。

## 2. 请求体实例提取

沿入口到请求 DTO、校验器、反序列化器、默认值、路由绑定和中间件，确认**最终在协议线上接受的字段与结构**。重点区分：必填/条件必填、嵌套对象、数组条目、字段别名、枚举、null 与缺省、HTTP multipart、WebSocket 消息类型。给出一份能满足已确认验证规则的**可读脱敏样例**；不要照搬可能包含真实凭据的调试日志。

没有请求体的接口 `request.state=none`，并提供具体原因；路径、查询参数或请求头仍应在正文完整列出。

## 3. 响应体实例溯源（P0）

对于每个接口，**不要在看完 Controller 返回类型后停止**：

1. 追踪成功分支返回值及 Service/DTO/Serializer/Postprocessing。
2. 查全局响应包裹、过滤器、字段转换、字段忽略、字段别名及空值处理；确认最终 JSON 是否包含例如 `data/code/message` 等顶层结构。
3. 检查条件响应及不同 HTTP 状态/业务状态，多态、分页和空结果。
4. 检查认证/授权、异常处理器、业务错误码、统一失败包裹器；为典型失败生成实证样例，不凭空添加 400/401/500。
5. 对服务端主动推送/事件，定位消息构造函数及公共字段拼装（例如事件序号、时间戳、会话号），再展开具体 payload，不能用 `{…}` 简写。
6. 对每条 `case` 填写真实 `evidence`（例如 `src/api/user.py:serialize_user` 或 `src/handlers/realtime.py:build_session_started`）。源码路径不是自动验证证明；必须实际阅读并核对。

## 4. 质量验证与保守策略

- 示例必须是**完整 JSON 数据结构**；不能把 `…` 放进 JSON，也不能用 `"..."` 代替未知字段。类型、可选字段、示例值应与实现相符。
- 对请求、成功、失败三类分别设置 `present / none / not_applicable / unknown`，并给出准确原因；`unknown` 表示需要人工确认，绝不是“已通过”的示例。
- 对多个重要响应事件及失败情况提供多 `cases`，不能只给理想路径。
- 代码本身不充分/实现会依赖运行时配置时先继续追踪；仍无法确认时写 `unknown`，反馈需核实文件和位置。
- 审核接口表、代码清单和已生成 `docs/api.md`，确保每个接口都出现三类章节。执行 `audit` 检查语法，再执行语义复核，不能只靠审计脚本证明数据真实。
- `scan_complete=true` 仅在实际完整扫描后设置；`deleted` 逐项附路由/注册点删除证据，绝不根据“未扫到”自行删除。
